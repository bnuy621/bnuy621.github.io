## Introduction
I'm not going to manually go through every single bit and crook of the PE file but i will provide references if you want to.

## Why understand it?
The reason one needs to understands the rough structure of PE file is that this is heavily used during static analysis of malware.

## Do i need to know everything
No. There are multiple tools out there to automate this process for you. However it is important to at least roughly know what it means so you can actually understand the output. 

## IMAGE_DOS_HEADER (64 bytes)
Link: <https://microsoft.github.io/windows-docs-rs/doc/windows/Win32/System/SystemServices/struct.IMAGE_DOS_HEADER.html>

All PE files contain the DOS header, this is the first 64 bytes of the file. The following image shows its structure

![](assets/posts/MAL/PE/dos_header.png)

The only things that you have to pay attention to are the first 2 bytes (signature) and the last four bytes which contain the offset to the coffheader/PE header. 

### e_magic (2 bytes)
This is located at the very start of the DOS header. These 2 bytes contain the signature for the DOS header with the values `4Dh 5Ah` which is `MZ`:

![](assets/posts/MAL/PE/dos_header_e_magic.png)


### e_lfanew (4 bytes)
This is located at offset `0x3C` (60 bytes) from the start of the DOS header. This is the offset of the PE header from the start of the file which allows the system to skip the DOS header and go directly to the  coffheader where the executable is.

![](assets/posts/MAL/PE/dos_header_e_lfanew.png)

### DOS message (43 bytes)
This is located 18 bytes from `e_lfanew`. This contains the message which is 43 bytes and usually contains the message "This program cannot be run in DOS mode."

![](assets/posts/MAL/PE/e_program_message.png)

## Coffheader AKA PE header
I will just call it PE header

### PE Header - signature (4 bytes)
This contains the  value `"PE\0\0` which are the letters `P` and `E` followed by two null bytes. This is the signature for a PE file. The value of this signature also determines the system it is operating on:
1. PE - 32 and 64 bit
2. NE - 16 bit
3. LE - Windows 3.X virtual driver
4. LX - OS/2.2.0 


![](assets/posts/MAL/PE/coffheader_signature.png)


### PE Header - File Header (20 bytes)
Link: <https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-image_file_header>
These are the next 20 bytes after the signature.This is a standard COFF file header in the following format. Note that the Windows loader limits the number of sections to 96.


![](assets/posts/MAL/PE/file_header.png)


#### machine (2 bytes)
This number identifies the target machine the program was designed for. As the value here is `64h 86h` this means it was designed for `AMD64`.

![](assets/posts/MAL/PE/file_header_machine.png)

#### numberOfSections (2 bytes)
This indicates the number of sections in the PE file with the max being 96.

![](assets/posts/MAL/PE/file_header_nosections.png)

#### File header - Characteristics (4 bytes)
These flags that indicate the attributes of the file, this is the link to the full list of them: <https://learn.microsoft.com/en-us/windows/win32/debug/pe-format#characteristics>

The more interesting ones that you should pay attention to being `0x2000` which indicates the file is a DLL and `0x0002` which indicates the file is an executable. 

![](assets/posts/MAL/PE/file_header_characteristics.png)

As the value is `0022`, this means that it is an executable image and it can handle more than 2GB of addresses. 


### PE Header - OptionalHeader
Link: <https://learn.microsoft.com/en-us/windows/win32/debug/pe-format#optional-header-image-only>
Every image file has an optional header that provides information to the loader. This header is optional in the sense that some files (specifically, object files) do not have it. For image files, this header is required. An object file can have an optional header, but generally this header has no function in an object file except to increase its size.

Note that the size of the optional header is not fixed. The SizeOfOptionalHeader field in the COFF header must be used to validate that a probe into the file for a particular data directory does not go beyond SizeOfOptionalHeader.

![](assets/posts/MAL/PE/optional_header.png)


#### OptionalHeader -Magic
The unsigned integer that identifies the state of the image file. The most common number is 0x10B, which identifies it as a normal executable file. 0x107 identifies it as a ROM image, and 0x20B identifies it as a PE32+ executable.

![](assets/posts/MAL/PE/optional_header_magic.png)


#### OptionalHeader - AddressOfEntryPoint
The address of the entry point relative to the image base when the executable file is loaded into memory. For program images, this is the starting address. For device drivers, this is the address of the initialization function. An entry point is optional for DLLs. When no entry point is present, this field must be zero.


![](assets/posts/MAL/PE/optional_header_addresentry.png)

#### OptinonalHeader - ImageBase
The preferred address of the first byte of image when loaded into memory; must be a multiple of 64 K. The default for DLLs is 0x10000000. The default for Windows CE EXEs is 0x00010000. The default for Windows NT, Windows 2000, Windows XP, Windows 95, Windows 98, and Windows Me is 0x00400000.

![](assets/posts/MAL/PE/optional_header_imgbase.png)



#### OptionalHeader - SectionAlignment
The alignment (in bytes) of sections when they are loaded into memory. It must be greater than or equal to FileAlignment/rawSectionAlignment . The default is the page size for the architecture.

![](assets/posts/MAL/PE/optional_header_secalign.png)

#### OptionalHeader - FileAlignment
The alignment factor (in bytes) that is used to align the raw data of sections in the image file. The value should be a power of 2 between 512 and 64 K, inclusive. The default is 512. If the SectionAlignment is less than the architecture's page size, then FileAlignment must match SectionAlignment.

![](assets/posts/MAL/PE/optional_header_secalign.png)


#### OptionalHeader - SizeOfImage
The size (in bytes) of the image, including all headers, as the image is loaded in memory. It must be a multiple of SectionAlignment.

![](assets/posts/MAL/PE/optional_header_imgsize.png)


#### OptionalHeader - SizeOfHeaders
The combined size of an MS-DOS stub, PE header, and section headers rounded up to a multiple of FileAlignment.


![](assets/posts/MAL/PE/optional_header_headersize.png)

#### OptionalHeader - DataDirectory

Link: <https://learn.microsoft.com/en-us/windows/win32/debug/pe-format#optional-header-data-directories-image-only>

![](assets/posts/MAL/PE/optional_header_datadir.png)

## Section Table
Link: <https://learn.microsoft.com/en-us/windows/win32/debug/pe-format#section-table-section-headers>

The common sections for a PE file are:
1. .text 
2. .rdata
3. .rsrc


Each row of the section table is, in effect, a section header. This table immediately follows the optional header, if any. Each section header (section table entry) has the following format, for a total of 40 bytes per entry. 

![](assets/posts/MAL/PE/section_table.png)

### Name (8 bytes)
This contains the name for the section. 

![](assets/posts/MAL/PE/s_Name.png)

### VirtualSize (4 bytes)
The total size of the section when loaded into memory. If this value is greater than SizeOfRawData, the section is zero-padded.

![](assets/posts/MAL/PE/s_Vsize.png)

### VirtualAddress (4 bytes)
For executable images, the address of the first byte of the section relative to the image base when the section is loaded into memory.

![](assets/posts/MAL/PE/s_VA.png)


### SizeOfRawData (4 bytes)
The size of the section (for object files) or the size of the initialized data on disk (for image files). 

![](assets/posts/MAL/PE/s_rawsize.png)

### PointerToRawData (4 bytes)
The file pointer to the first page of the section within the COFF file. 

![](assets/posts/MAL/PE/s_ptrraw.png)

### PointerToRelocations (4 bytes)
The file pointer to the beginning of relocation entries for the section. This is set to zero for executable images or if there are no relocations.

![](assets/posts/MAL/PE/s_reloc.png)

### PointerToLinenumbers (4 bytes)
The file pointer to the beginning of line-number entries for the section. This is set to zero if there are no COFF line numbers. This value should be zero for an image because COFF debugging information is deprecated.

![](assets/posts/MAL/PE/s_ptrlineno.png)

### NumberOfRelocations (2 bytes)
The number of relocation entries for the section. This is set to zero for executable images.

![](assets/posts/MAL/PE/s_noreloc.png)

### NumberOfLinenumbers (2 bytes)
The number of line-number entries for the section. This value should be zero for an image because COFF debugging information is deprecated.

![](assets/posts/MAL/PE/s_nolineno.png)

### Characteristics (4 bytes)
The flags that describe the characteristics of the section. The link to the full list of flags: <https://learn.microsoft.com/en-us/windows/win32/debug/pe-format#section-flags>

![](assets/posts/MAL/PE/s_char.png)

As the `.text` section is executable, the bit for `IMAGE_SCN_MEM_EXECUTE` is set to `1`.


## Import table
Link: <https://learn.microsoft.com/en-us/windows/win32/debug/pe-format#import-directory-table>

This states the libraries and functions the executable imports. It is useful for malware analysis as it allows one to infer what are the functions of the malware. This is usually located in 
`.rdata`

The import information begins with the import directory table, which describes the remainder of the import information.

![](assets/posts/MAL/PE/IDT.png)


### Import Lookup Table RVA

The RVA of the import lookup table. This table contains a name or ordinal for each import.
![](assets/posts/MAL/PE/lookuptableRVA.png)

### Time/Date Stamp
The stamp that is set to zero until the image is bound. After the image is bound, this field is set to the time/data stamp of the DLL.
![](assets/posts/MAL/PE/import_TDS.png)

### Forwarder Chain
The index of the first forwarder reference.
![](assets/posts/MAL/PE/import_Fchain.png)

### Name RVA
The address of an ASCII string that contains the name of the DLL. This address is relative to the image base.
![](assets/posts/MAL/PE/import_nameRVA.png)

### Import Address Table RVA (Thunk Table)
The RVA of the import address table. The contents of this table are identical to the contents of the import lookup table until the image is bound.
![](assets/posts/MAL/PE/import_ftRVA.png)


## Import lookup table
An import lookup table is an array of 32-bit numbers for PE32 or an array of 64-bit numbers for PE32+. Take note that bit 31 is the most significant bit for PE32 and bit 63 is the most significant bit for PE32+.

### Ordinal/Name Flag
If this bit is set, import by ordinal. Otherwise, import by name. Bit is masked as 0x80000000 for PE32, 0x8000000000000000 for PE32+.
![](assets/posts/MAL/PE/ILT_Oflag.png)


### Ordinal number
A 16-bit ordinal number. This field is used only if the Ordinal/Name Flag bit field is 1 (import by ordinal). 

### Hint/Name Table RVA
A 31-bit RVA of a hint/name table entry. This is used only when the Ordinal/Name Flag bit field is 0 (import by name).
![](assets/posts/MAL/PE/ILT_nameRVA.png)

## Hint/Name table
One hint/name table suffices for the entire import section.

### Hint (2 bytes)
An index into the export name pointer table. A match is attempted first with this value. If it fails, a binary search is performed on the DLL's export name pointer table.
![](assets/posts/MAL/PE/HT_hint.png)

### Name
An ASCII string that contains the name to import. 
![](assets/posts/MAL/PE/HT_name.png)


## Import address table
Link: <https://learn.microsoft.com/en-us/windows/win32/debug/pe-format#import-address-table>
This is the exact same as the import lookup table except that when running the program, its entries are filled with the actual address of the symbols being imported.

![](assets/posts/MAL/PE/IAT.png)

## Export address table
This contains the actual addresses of the exported functions and data within the executable code and data sections.
![](assets/posts/MAL/PE/EAT.png)

![](assets/posts/MAL/PE/EAT2.png)

## Name pointer table
This contains pointers to the public export names in ascending order.
![](assets/posts/MAL/PE/NPT.png)

![](assets/posts/MAL/PE/NPT2.png)

### Ordinal table
This contains ordinals that correspond to members of the name pointer table. The correspondence is by position; therefore, the name pointer table and the ordinal table must have the same number of members. Each ordinal is an index into the export address table.

![](assets/posts/MAL/PE/OT.png)

![](assets/posts/MAL/PE/OT2.png)

### Export name table 
A series of null-terminated ASCII strings. Members of the name pointer table point into this area. These names are the public names through which the symbols are imported and exported
